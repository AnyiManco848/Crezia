## Procedimiento exacto (PowerShell, desde la raíz del repo)

El backend de pruebas y el front son dos procesos; el front lo levanta Playwright solo.

```powershell
# 1. Comprueba que .env.test NO apunta a la base real (no toca la base)
npm run db:test:check

# 2. Terminal A: backend contra crezia_test (déjalo corriendo)
npm run dev:test
#    Comprobación: http://localhost:3000/api/health responde {"status":"ok"}

# 3. Terminal B: E2E del front
cd frontend
$env:E2E_TEST_DB_CONFIRMED = "true"     # confirmas que el backend usa la base de PRUEBAS
$env:E2E_EMAIL = "test@crezia.com"      # usuario del seed
$env:E2E_PASSWORD = "Test123*"
npm run e2e

# 4. (Opcional, desde la raíz) borra las filas E2E que quedaron con deleted_at
npm run db:test:purge-e2e
```

Qué hace falta y qué no:

| Pieza | Necesidad |
|---|---|
| `VITE_API_URL` | **No hace falta.** En desarrollo el front usa `http://localhost:3000` por defecto (`frontend/src/build/csp.ts`) y no existe `frontend/.env`. Solo se define si el backend de pruebas está en otro puerto (y entonces también `E2E_API_URL`). |
| `VITE_ALLOW_LOCAL_API` | **No hace falta.** Es solo para probar un *build de producción* (`npm run build` + `preview`) contra una API local. Nunca en Vercel. |
| CORS | **No hace falta tocar nada.** Playwright abre el front en `http://127.0.0.1:5173` y el backend permite por defecto `http://localhost:5173` y `http://127.0.0.1:5173` (`src/config/cors.ts`). Si el front corriera en otro origen, define `CORS_ORIGINS` al arrancar el backend de pruebas. Comprobado: `Access-Control-Allow-Origin: http://127.0.0.1:5173`. |
| Servidor del front | Lo arranca Playwright (`npm run dev -- --host 127.0.0.1`, `reuseExistingServer: true`) y lo cierra al terminar; si ya hay uno en el 5173 lo reutiliza. |
| Límites de intentos | `TEST_MODE=true` sube el del login a 1000 y `.env.test` el del registro (`REGISTER_RATE_LIMIT_MAX=1000`); los E2E no los alcanzan. |

Al terminar, cierra el backend de la terminal A (Ctrl+C). Si lo arrancaste en segundo plano, hay que cerrar toda la cadena `npm` → `tsx watch` → `node` (en esta ejecución: `taskkill /PID <pid del npm> /T /F`) y comprobar con `netstat -ano | findstr ":3000 :5173"` que los puertos quedan libres.

Sin `E2E_TEST_DB_CONFIRMED=true`, sin credenciales o sin backend respondiendo, las pruebas se saltan con un aviso (`frontend/e2e/support.ts`).

## Fallas encontradas y su arreglo

Ninguna es defecto del producto; **no se abrió DEF-011**. Todas eran defectos de las pruebas y se corrigieron solo en `frontend/e2e` (sin tocar código de producción).

| # | Prueba | Causa | Arreglo aplicado |
|---|---|---|---|
| 1 | `categories.spec.ts` «crear, editar y eliminar una categoría» | `getByRole('cell', { name })` coincidía con **dos** celdas (la del nombre y la de acciones, cuyo nombre accesible incluye los botones «Editar <nombre>»; la coincidencia por defecto es por subcadena). *Strict mode* de Playwright lo rechaza. | `{ name, exact: true }` en la celda del nombre y en la de `currentName`. |
| 2 | `goals.spec.ts` «valida el formulario antes de enviar» | `getByText('Selecciona una categoría')` coincidía con la `<option value="">` del desplegable y con el `<span role="alert">` del error. | `form.getByRole('alert').filter({ hasText: 'Selecciona una categoría' })`. |
| 3 | `movements.spec.ts` «pide la lista con page y limit…» | Carrera: el `beforeEach` ya cargó `/movimientos`, así que la petición ocurrió antes de que la prueba llamara a `page.waitForRequest`; nunca llega otra y agota los 30 s. | `const [request] = await Promise.all([page.waitForRequest(…), page.reload()])`. |
| 4 | `register.spec.ts` (todo el archivo) | `path.resolve(__dirname, …)`: `frontend` es un módulo ES (`"type": "module"`) y `__dirname` no existe → `ReferenceError` al cargar; Playwright abortaba **toda** la corrida. | `path.dirname(fileURLToPath(import.meta.url))` (import de `node:url`). |
| 5 | `categories.spec.ts` y `accounts.spec.ts` «pide la lista con page y limit…» (**intermitentes**) | Misma carrera que la 3, detectada en la primera corrida de `npm run e2e` tras los cuatro arreglos: fallaba `categories` (antes pasaba). `waitForResponse` se registraba después de que el `beforeEach` cargó la página; pasaba o fallaba según llegara antes el título o la respuesta. Medido: en 16 repeticiones fallaron 6 y 10 (dos tandas) entre las dos pruebas. | `const [response] = await Promise.all([page.waitForResponse(…), page.reload()])` en ambas. |

### Auditoría del patrón «esperar una petición después de que el `beforeEach` ya cargó la página»

Se revisaron todos los `waitForRequest`, `waitForResponse` y `page.on('request')` de `frontend/e2e`:

| Lugar | Veredicto |

## Qué dejan los E2E en `crezia_test`

- **Activo sin limpiar: nada.** Tras todas las corridas: 0 usuarios `@e2e.crezia.test` y 0 categorías, metas, movimientos o cuentas `E2E …` sin `deleted_at`. Los usuarios del registro se borran de verdad al terminar el archivo (`scripts/test-db-clean-e2e-users.ts`).
- **Lo que sí queda:** filas con `deleted_at` (la API solo hace *soft delete*); crece con cada corrida (en la prueba de 10 repeticiones, +10 metas y +20 categorías).
- **Cómo limpiarlas:** `npm run db:test:purge-e2e` (uso, condiciones y protecciones en [`purga-e2e.md`](purga-e2e.md)). Tras las corridas de esta sesión la purga devolvió la base **exactamente** a su estado inicial: categorías 31 (24 borradas), cuentas 11 (10), metas 11 (10), movimientos 130 (125) y 1 usuario (el semilla).
- No se purgan las filas de las pruebas de API (`PW …`), que también se acumulan.
